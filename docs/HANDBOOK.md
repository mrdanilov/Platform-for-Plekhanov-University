# Памятка по проекту

Подробная памятка для тех, кто работает с кодом: как запускать, как
устроены справочники, что означает каждая настройка и почему именно так.
Для короткого описания проекта достаточно README.md в корне.

Этот файл не пересказывает всё подряд — он отвечает на вопрос «куда
смотреть и что делать», а README отвечает на вопрос «что это и зачем».

## Структура папок

Проект целиком лежит в одной папке. Внутри неё:

```
timetable/                     ← корень проекта, здесь README и manage.py
├── manage.py                  ← точка входа: python manage.py ...
├── db.sqlite3                 ← вся база расписания
├── config/                    ← настройки Django (не логика)
│   ├── settings.py            ←   база, статика, безопасность, HTTPS
│   ├── urls.py                ←   какие адреса на какие страницы
│   └── wsgi.py                ←   вход для сервера
├── schedule/                  ← всё логика расписания
│   ├── models.py              ←   таблицы: группы, предметы, занятия, пары
│   ├── views.py               ←   что отвечает на каждый адрес
│   ├── templates/schedule/    ←   как выглядит страница
│   ├── static/schedule/       ←   стили и картинки
│   ├── exports.py             ←   выгрузка в CSV и палитра предметов
│   └── raw_lessons.py         ←   разбор занятий без группы
├── tools/                     ← вспомогательные скрипты
│   ├── show_lan.py            ←   показ коллегам в локальной сети
│   ├── watchdog.py            ←   сторож: поднимает платформу, если она упала
│   └── backup.sh              ←   бэкап базы
```

**Ключевое, что стоит запомнить.** Проект — это `timetable`, и всё внутри него
принадлежит ему, включая папку `schedule/`. Имя `schedule` — только название
подпапки внутри проекта, а не отдельный проект. Отдельного проекта с таким
именем на диске нет.

Разделение на `config/` и `schedule/` — обычная раскладка Django: в `config`
настройка запуска, в `schedule` сама логика. Переименовывать папку не нужно,

**Где что искать.** Поменять данные или внешний вид — `schedule/`. Поменять
настройки запуска, базу или статику — `config/`. Что-то разово выполнить —
`tools/`.

## Запуск (Windows, PowerShell)

```powershell
cd C:\Users\Den\timetable
.venv\Scripts\activate
python manage.py runserver
```

Открыть: http://127.0.0.1:8000/

Без активации:

```powershell
cd C:\Users\Den\timetable
.venv\Scripts\python.exe manage.py runserver
```

### Правка не появилась на странице — перезапусти сервер

Шаблоны Django при `DEBUG=1` перечитываются сами, а при `DEBUG=0`
кэшируются **до перезапуска процесса**. Статические файлы в обоих случаях
отдаются свежими, поэтому картина обманчива: стили обновились, а разметка
и скрипт остались старыми. Ошибок при этом нет, страница выглядит целой.

Отличить можно по 404-странице: у `DEBUG=1` она длинная и перечисляет
`urlpatterns`, у `DEBUG=0` — пустая.

Правило простое: **после правки шаблона перезапусти `runserver`**, если
`DJANGO_DEBUG` не равен `1`. Флаг `--noreload` к шаблонам отношения не
имеет — он отключает только автоперезапуск по файлам Python.

Для локальной сети запускай так, иначе изменения тоже не подхватятся:

```powershell
$env:DJANGO_DEBUG = "1"
$env:DJANGO_ALLOWED_HOSTS = "192.168.1.10,10.0.0.5,127.0.0.1,localhost"
.venv\Scripts\python.exe manage.py runserver 0.0.0.0:8000 --noreload
```

Обязательно указывай `0.0.0.0`, а не конкретный адрес: `runserver
192.168.1.10:8000` слушает ровно один адаптер, и при смене IP из-за DHCP
сервер станет недоступен, хотя процесс будет жив.

## Главное меню

Блок расписания виден сразу. По умолчанию сетка **пустая**: дни недели в строках,
пары в колонках на месте, все ячейки пустые — ни одной строки с предметом, пока
не выбран фильтр. Над блоком плашка-подсказка и три кнопки:

| Кнопка | Что делает |
|---|---|
| **Группы** | список групп, выбор — расписание этой группы |
| **Пары** | список пар (1-я, 2-я …), выбор — все занятия этой парой |
| **Преподаватели** | список ФИО, выбор — расписание этого преподавателя |

Список открывается всплывающим окном с поиском. После выбора блок обновляется
подгрузкой, без перезагрузки страницы. Стрелки `«` `»` переключают недели.

Без JavaScript всё работает обычными ссылками: `/?view=group&id=3`,
`/?view=teacher&id=5`, `/?view=pair&id=2`.

## Шапка

- **Логотип** слева от навигации, прямо на синей полосе — без подложки и рамки:
  сетка недели в четыре строки и слово «Расписание», 240×48px,
  `schedule/static/schedule/img/logo.png`
- Картинка 800×160, RGBA, целиком белая на прозрачном фоне. Белым он идёт уже
  в исходнике, поэтому на синей полосе и на почти чёрной полосе тёмной темы
  надпись читается одинаково, а фильтр `brightness` не нужен
- Кадр заполнен содержимым без пустых полей. Это не украшательство: при
  пустых полях по краям на шапке высотой 82px логотип превращается в
  неразличимую полосу. За это отвечает проверка `test_logo_asset_exists_and_is_cropped`
- Пропорции 5:1 выдержаны во всех брейкпоинтах. У картинки заданы явные
  `width`, `height`, `min`/`max` и `flex-basis` — во flex-контейнере иначе
  она вытягивается по высоте и сплющивается по ширине
- Логотип не содержит чужих торговых марок: репозиторий публичный, и там не
  должно быть эмблемы или названия чужого вуза
- Навигация: Главная, На сегодня, Университет
- **Переключатель языка RU / UZ** справа. Ссылка ведёт на `/lang/?lang=uz&next=<адрес текущей
  страницы>`: язык запоминается в cookie на год, а выбранная группа или пара в адресе
  не теряется
- **Кнопка темы** ☾ / ☀ — светлая и тёмная. Выбор хранится в `localStorage`
  и применяется до отрисовки, поэтому страница не мигает
- **Кнопка «Войти»** в крайнем правом углу — ведёт в админку

Высота полосы 82px на десктопе, на мобильных логотип 36px и 28px.
Проверки логотипа — `schedule/test_header.py`: белый по пикселям (декодируется
PNG вручную, Pillow в проекте не нужен), пропорции, обрезка по контенту,
одинаковые `width`/`min`/`max` в каждом брейкпоинте.

## Режим «Пары»

Фильтр «Пары» выбирает конкретную пару, поэтому занятия у неё всегда в одной
колонке. Раньше карточки шли вертикальным столбиком в узкой ячейке, а остальные
семь колонок были пустыми — строка растягивалась по высоте, а полезная ширина
падала.

Теперь для этого режима таблица не рисуется вовсе. Дни остаются блоками, а
занятия идут сеткой карточек на всю ширину:

- `grid.cards_mode` в `schedule/grid.py` — переключатель. Он включается только
  для «Пар» (`build_grid(..., cards=True)`) и только когда непустая колонка
  ровно одна. У группы с одной парой в неделю привычная таблица сохраняется
- Шаблон `schedule/templates/schedule/_cards.html`, подключается из `_block.html`
- Сетка `repeat(auto-fill, minmax(165px, 1fr))`: карточки переносятся по мере
  заполнения, `minmax` не даёт им растянуться нечитаемыми полосами. На
  мобильных `minmax(140px, 1fr)`
- Шапка с номерами пар убрана: пара и её время вынесены в заголовок над
  карточками, сегодняшний день обведён синим
- Время пары печатается в правом нижнем углу каждой карточки в обоих режимах
- Пустая пара (нечётная неделя, пара без занятий) откатывается на обычную
  таблицу — иначе на ней просто нечего было бы показать
- Печать: тени убираются, рамки остаются, блок дня не рвётся между страницами
- Фрагмент `/block/` ведёт себя так же, поэтому смена фильтра без перезагрузки
  показывает ту же раскладку

## Время пары в карточке

Время выводится внутри карточки занятия во всех режимах — и в таблице, и в
сетке карточек:

- Разметка: `<div class="lesson-time">` последним блоком внутри карточки,
  значение берётся из `cell.lesson.lesson_time`, то есть от той же пары,
  а не от первой в списке
- Карточка получает `position: relative`, блок времени — `absolute` с отступом
  8px справа и снизу. Так угол не зависит от высоты карточки
- Шрифт 11px, `font-weight: 600`, цвет `rgba(0, 0, 0, .55)` — одинаково
  читается на светлой заливке предмета в обеих темах и не перекрашивается
  белым в тёмной
- Чтобы время не наезжало на аудиторию, снизу у карточки отступ больше, чем
  сверху (`5px 6px 15px` в таблице, `7px 9px 18px` в сетке), а подписи в
  таблице дополнительно отступлены справа на 46px

## Информация о университете

Отдельная страница `/university/`, пункт «Университет» в шапке. Не модальное окно:
адрес можно отправить ссылкой, страница листается вместе с шапкой и работает без JS.

- Шаблон `schedule/templates/schedule/university.html` наследует общий каркас
  `base.html`, стили — внизу `style.css`
- Слева контакты и карта (iframe Яндекс Карт, `loading="lazy"`, `border-radius`),
  справа форма. Колонки в `grid-template-columns: 1fr 1fr`, на ширине до 900px
  складываются в одну, кнопка растягивается
- Контакты лежат в `schedule/contacts.py`: адрес, два телефона с подписями,
  почта школы и веб-мастера. Подписи переведены в `schedule/i18n.py`
- Запрос к карте (`MAP_QUERY`) переписан латиницей без диакритики: апостроф
  в «koʻchasi» поиском по карте не распознаётся. Экранируется через
  `urllib.parse.quote`, а не заменой пробелов: одинарная кавычка в запросе
  иначе попадает в атрибут `src` неэкранированной
- Ссылки телефонов и почты окрашены в `--blue-deep`, а не в `--blue`: блок
  лежит на полупрозрачной панели, и поверх фото `--blue` давал 3.9:1 —
  ниже порога WCAG. Проверяет `UniversityContactsContrastTests`
- Форма — обычный POST без JavaScript: при успехе редирект на `?sent=1`,
  при ошибке страница перерисовывается с кодом 400 и подсказкой
- **Проверка человека**: арифметический пример на картинке, как на других
  сайтах. Рисуется на сервере в `schedule/captcha.py` — PNG собирается через
  `zlib` и `struct`, Pillow не нужен. Плюс ссылка «Другой пример» (`?refresh=1`)
- Пример и ответ лежат в сессии, клиенту отдаётся только картинка. Вопрос
  одноразовый: после попытки он удаляется, при ошибке выдаётся новый — иначе
  один пример можно было бы подбирать перебором. Ответ не меньше 2, потому что
  ноль с буквой O путают, а единица угадывается
- Ограничение: арифметическая капча отсекает тупой спам, но не целевой. Если
  форма станет важной, нужна настоящая reCAPTCHA или hCaptcha с ключами сайта
- Обращения сохраняются в модель `ContactMessage` и видны в админке
  («Обращения», с поиском и фильтром по дате). Серверная проверка требует имя,
  корректную почту, текст, согласие и верный ответ на пример; CSRF — штатный
- Длинный ввод обрезается по максимальной длине поля, а не роняет страницу

## Контрастность

Цвета подписей проверяются по WCAG. Мелкий текст (время пары, даты под днями,
нижняя подпись, подпись в списке) использует отдельную переменную
`--muted-strong`, а не общий `--muted`:

| Элемент | Светлая тема | Тёмная тема |
|---|---|---|
| Время пары `08:00` на серой шапке | `#38485a` / `#e7e6e6` — **7.5:1** | `#c4d0dc` / `#2c3844` — **7.6:1** |
| Дата под днём | `#38485a` / `#f2f2f2` — **8.4:1** | `#c4d0dc` / `#26313c` — **8.5:1** |
| Нижняя подпись, подпись в списке | **9.4:1** | **10.3:1** |

Было `--muted: #6b7a8d` — 3.5:1 на шапке и 3.9:1 под днём, то есть ниже порога
WCAG AA 4.5:1. Теперь `--muted: #4a5b6d` (≥5.6:1), мелкие подписи —
`--muted-strong`. Обе темы проверяются тестами: `schedule/test_ui.py` считает
контраст по формуле WCAG и падает, если значение падает ниже 4.5 (AA) или 7.0 (AAA).

## Мобильная версия

| Ширина | Что меняется |
|---|---|
| ≤ 900px | логотип уменьшается, навигация переносится на вторую строку и скроллится |
| ≤ 620px | кнопки фильтров во всю ширину, колонка дней закреплена слева, шапка таблицы прилипает сверху, таблица скроллится по горизонтали, всплывающий список занимает весь экран |
| ≤ 400px | ещё компактнее таблица, у «Войти» скрывается иконка |
| `(hover: none)` | отключается подсветка кнопок при тапе — на мобильных она «залипает» |

Колонка дней закреплена `position: sticky; left: 0` с тенью-разделителем, поэтому
при прокрутке вбок всегда видно, какой это день. Минимальная ширина таблицы —
620px, чтобы колонки не схлопывались в нечитаемые полоски.

## Вид таблицы

Дни в строках (`Понедельник` … `Суббота`), пары в колонках — как в файле
`Расписание_как_на_фото.xlsx`: серые шапки (`#e7e6e6` / `#f2f2f2`), тонкие рамки,
всё по центру. Пустые ячейки помечены классом `slot-empty` и отличаются фоном.

В ячейке видно: предмет, тип, группу (кроме вида «Группы»), преподавателя (кроме
вида «Преподаватели»), аудиторию. Замены помечены красным.

## Админка

Кнопка «Войти» → http://127.0.0.1:8000/admin/

Логин и пароль задаёт администратор при развёртывании. Учётной записи с
паролем по умолчанию в проекте нет — перед выкладкой создай свою:

```powershell
python manage.py createsuperuser
```

Разделы:

| Раздел | Что |
|---|---|
| Занятия | всё расписание; преподаватель, аудитория и тип правятся прямо в списке; массовые действия «сдвинуть день недели ±1» |
| Замены | кто вместо кого и в какой день. Только чтение |
| Группы | группы и курсы |
| Преподаватели | ФИО, должность, кафедра, контакты |
| Предметы | название, сокращение, цвет подложки |
| Аудитории | номер, корпус, вместимость |
| Типы занятий | лекция, практика, семинар… |
| Время пар | номер и интервал пары; задаётся один раз |
| Замены | кто вместо кого и на какую дату |

Ссылка «В расписание» из админки: `/admin/schedule/`.

Правило: у группы в один слот (день + пара + чётность) может быть только одно
занятие — об этом сообщает форма.

## Ввод расписания вручную

Импорт из файла удалён: в браузере сотрудницы заполняют базу через
админку. Причины две — кнопка «Проверить файл» писала данные в базу, пока
показывала «будет создано» (audit_todos/01), и формат файла вуза система
не понимала.


1. Группы и курсы → 2. Предметы → 3. Преподаватели → 4. Аудитории →
5. Времена пар → 6. Занятия

Справочники заполняются один раз, занятия — по одному через форму
«Добавить». Кнопка «Сохранить и добавить ещё» оставляет форму открытой:
если идти по порядку «лист → день», день и пара повторяются и ввод
ускоряется.

Команда python manage.py check_duplicates ищет дубли в справочниках —
после ручного ввода они появляются, когда сотрудница написала «Финансы»
и «финансы» двумя строками.

## Загрузка файла из консоли

Если всё же нужно залить в базу файл вуза целиком, это делается из
терминала, а не из браузера:

```bash
# сначала посмотреть, что будет записано, ничего не меняя
python manage.py load_week_schedule "C:\путь\расписание.xlsx" --dry-run

# записать
python manage.py load_week_schedule "C:\путь\расписание.xlsx"

# очистить прежнее расписание и загрузить заново
python manage.py load_week_schedule "C:\путь\расписание.xlsx" --replace

# то же самое без вопроса (для скриптов и cron)
python manage.py load_week_schedule "C:\путь\расписание.xlsx" --replace --noinput
```

Чем это отличается от удалённого «Импорта»:

- запускается только из командной строки, кнопки в браузере нет;
- сначала печатает счётчики, а на `--replace` ещё и спрашивает подтверждение
  (или молчит при `--noinput`) — удалённый импорт показывал «будет создано»
  и писал сразу;
- `--replace` удаляет прежнее расписание, поэтому перед ним нужна копия
  базы;
- без `--replace` повторный запуск не падает: занятия, которые уже есть,
  пропускаются.

Файл вуза — сетка: пять листов (1–4 курс и ОЗФ), строки это дни недели,
а группы стоят парами столбцов «предмет» и «аудитория». Команда сама
достаёт оттуда группу, курс, профиль, день, пару, предмет, тип занятия,
преподавателя с должностью и аудиторию с корпусом.

Что команда понимает с опечатками файла, потому что они там есть:
«ст перп.» без буквы, «пакт.зан.» вместо «практ.зан.», слипшееся
«бизнеселекц.)», ФИО без должности («Саттарова Б.Ш.»), время через
двоеточие («15:30-16:50») и без него.

Известные ограничения:

- **кураторский час пропускается** — это не занятие, у него нет номера
  пары;
- **время пары берётся самое частое**: в среду и четверг в файле сдвиг на
  5 минут, а «пара» в системе одна на неделю; команда предупреждает,
  сколько таких строк было;
- **группа «4303-4304» остаётся объединённой** — в файле она одной
  колонкой, и обе группы получают одно и то же занятие;
- **чётность недель берётся из семестра** в шапке листа: «на 3 семестр» →
  нечётные недели. Если в шапке смешаны и чётные, и нечётные семестры
  (обычно так у ОЗФ: «на 1,3,5,7,9 семестр» — все нечётные, это
  отрабатывается), недели различить нельзя, и всё встаёт «каждую
  неделю»;
- **кураторский час не загружается вовсе** — в системе для него нет
  места: у него своё время (11.50–12.30, 14.00–14.40), своя аудитория и
  ФИО куратора, а не предмет и пара.

## Выгрузка Excel

Кнопка «Excel» в шапке блока. Получается файл в том же формате, что и
шаблон-оригинал.

Адрес один: `/export/timetable.xlsx`, имя маршрута `export_xlsx`. Раньше на
ту же вьюху вешал ещё и `export/current.xlsx` — адрес удалён: нигде не
использовался и наружу не публиковался. CSV — отдельный адрес
`/export/timetable.csv` (`name='export'`), плоская выгрузка всего расписания,
и в отличие от книги он публичный.

### Кому доступна книга

Всем, как и CSV. Ограничение «только для сотрудников» стояло зря: в книге
ровно те же данные, что и в публичном CSV — группа, предмет, аудитория,
преподаватель. Телефона и почты нет ни там, ни там.

Закрывать пришлось бы только от цены сборки, и сделано это не запретом:

| Средство | Значение | Зачем |
|---|---|---|
| rate limit | 30 запросов в минуту с одного IP | без него бот выедает процессор |
| кэш | 60 секунд | одноклассники не собирают одну книгу десять раз |

Замер на текущей базе (6 групп, 120 занятий): сборка книги — около 20 мс,
попадание в кэш — около 1.4 мс, выигрыш в 13 раз. С ростом базы (сотни
занятий) сборка дорожает, а кэш остаётся тем же, так что выигрыш растёт.

Плата за кэш: после правки расписание в книге может появиться не сразу, а
с задержкой до минуты. Для выгрузки это незаметно.

### Формульная инъекция

Excel считает содержимое ячейки формулой, если оно начинается с `=`, `+`, `-`
или `@`. Поэтому предмет с названием вроде `=HYPERLINK("http://подделка...",...)`
раньше попадал в книгу как **настоящая формула**: сотрудник открывает файл,
переходит по ссылке — и с его компьютера уходят данные. Заменяется только
сотрудником через админку: сценарий тот, в котором
пользователь доверяет содержимому файла.

Защита в `schedule/formula_guard.py`, работает в обеих выгрузках:

- **в книге** ячейке принудительно ставится текстовый тип, само значение не
  меняется и не видно отличий;
- **в CSV** ставится префикс-апостроф — кавычки там не помогают, Excel
  формулу увидит и внутри них.

Заодно причина держать файл одним объектом: все ячейки идут через один
помощник, чтобы не забыть про новую (задача `13`).

Проверяется `schedule/test_export_protection.py`.


## Пауза на кнопке Excel

После скачивания кнопка блокируется на 30 секунд и показывает обратный отсчёт,
чтобы человек не клацал её подряд. Лимит на 30 запросов в минуту с IP остаётся
страховкой: пауза живёт в браузере и её можно обойти, лимит — нет.

Устройство:

- длительность задана в шаблоне: `data-cooldown="30"` на кнопке, а не зашита
  в скрипт; меняется одним атрибутом;
- клик ловится делегированием на `document`, а не слушателем на самой кнопке.
  Блок расписания перерисовывается через `innerHTML` при смене группы, преподавателя
  или недели, и слушатель на кнопке после этого молча перестал бы работать;
- остаток хранится в `localStorage` под ключом `schedule_export_cool_until`
  как метка времени. В памяти вкладки и в хранилище берётся максимум: свежий
  перезапуск страницы подхватывает остаток, а приватный режим, где
  `localStorage` бросает исключение, не ломает страницу и работает внутри вкладки;
- вторая вкладка видит ту же паузу, потому что остаток перечитывается каждый
  тик, а не берётся из памяти;
- `href` остаётся на месте: блокируется только левый клик. Правый клик и
  средняя кнопка работают как обычно — это осознанно, пауза не притворяется
  защитой;
- после перерисовки блока `paintCooldown()` вызывается сразу, иначе до
  следующего тика кнопка секунду выглядела бы обычной, хотя клик уже заблокирован.

Проверяется дважды. `ExportCooldownButtonTests` смотрит разметку: есть ли
атрибуты, переведена ли подпись секунд, объявлены ли стили. Этого мало — такая
проверка не заметит, что отсчёт не тикает. Поэтому сам скрипт ещё и
исполняется: `schedule/tests_js/cooldown.js` вырезает его из шаблона и гоняет
против подменённых `document`/`localStorage`/`Date` с перемоткой времени,
включая приватный режим. Тест `schedule/test_cooldown_js.py` пропускается,
если node не установлен, — Django от node не зависит.

Вручную: `node schedule/tests_js/cooldown.js`


## Замены

Если преподавателя заменили, занятие уходит из его расписания на эту неделю
и по появившемуся у заменяющего. Дата замены должна совпадать с днём недели
занятия.

### Причина замены не показывается

В расписании видна только метка «замена». Сама причина — «болезнь», «диарея»,
семейные обстоятельства — остаётся в модели и в админке, но не попадает
ни в один публичный вывод: ни в сетку, ни в карточки, ни на страницу дня.

Это осознанно: причина — личная информация преподавателя, и в расписании для
студентов ей не место.

Чтобы это не вернулось при правке шаблона, причина убрана не только из
разметки, но и из контекста — из `grid.py` и из контекста страницы дня в
`views.py`. Чтобы она не утекла через файл, проверено и содержимое выгрузок:
CSV и Excel её не содержат, тест разбирает книгу, а не ищет по байтам.

Проверяется `schedule/tests.py`: `test_substitution_reason_not_shown`
(сетка, карточки, страница дня, CSV), `test_substitution_reason_not_in_xlsx`,
`test_substitution_reason_kept_in_admin` и `test_reason_is_not_rendered`
в `test_pair_cards.py` — последний проверяет, что остались и стили, и
разметка: если бы стили исчезли, а разметка нет, причина вернулась бы при
следующей правке.

### Фон страницы и высота блоков

Фон — фотография под приглушающим слоем `--bg-veil` (`linear-gradient` поверх
`url()`). Два решения, которые важно не откатывать:

- **`background-attachment` не используется.** С `fixed` фотография
  привязывается к окну, и на странице короче окна она рисуется полосой, а поля
  остаются ровной заливкой. Обычное поведение тянет снимок на всю высоту
  документа, и на телефоне вдобавок не тормозит при прокрутке.
- **Нет режима подмешивания.** Раньше стоял `background-blend-mode: multiply`
  со светлой подложкой — снимок выходил пересвеченным, почти белым, без деталей;
  в тёмной теме он наследовался и гасил фотографию целиком. Прозрачность
  вуали задаётся явно: светлая `rgba(19,47,92,.20)`, тёмная `rgba(10,20,34,.34)`.

Фильтра размытия в проекте нет — он зашит в саму фотографию, и уменьшать его
средствами разметки нечем.

Размеры блоков подняты по вертикали: ячейка пары 62 → 74px, шрифт занятия
11 → 12px, отступы панели 16 → 22px и карточки 16 → 20px. Лестница для широких
экранов выросла согласованно: 1800px → 100px, 2400px → 124px, 3200px → 148px.
Проверяет `schedule/test_wide.py` и `schedule/test_appearance.py`.

## Два занятия в одну пару

У группы бывает две пары в один день на один номер — например, когда пара
делится между преподавателями. Такое разрешено: добавьте второе занятие
отдельной строкой с той же группой, днём и парой, но другим предметом.

Ограничение в базе уникально **по занятию**, а не по паре:
`(группа, день, пара, неделя, предмет)`. Поэтому два разных предмета в одной
ячейке сохраняются, а точная копия занятия — по-прежнему отклоняется как
опечатка.

Вывод в порядке показа такой:

- в таблице ячейка содержит оба блока, разделённых линией
  (`style.css`, `.lesson + .lesson`) — рендерер к этому был готов изначально,
  список занятий в ячейке существовал и раньше;
- в Excel оба занятия склеиваются в одну ячейку через пустую строку;
- в CSV выходят двумя строками.

Проверяет `schedule/test_two_lessons_slot.py` (13 тестов).

## Время в углу ячейки и метка «замена»

Время пары стоит в правом нижнем углу блока занятия поверх подписей. Место под
него резервируется отступом справа у `.lesson-meta`, и размер этого отступа —
не украшение, а расчёт:

- подпись «08:00–09:20» на 11.5px жирным занимает около **63px**;
- плюс отступ угла **7px**;
- итого нужно **70px**. Стояло **48px** — подписи наезжали на время.

Особенно это было видно на замене: метка «замена» добавляет строку сверху.
Здесь накопилось три разные причины, и каждую тянуло по очереди:

1. **Запас справа был меньше нужного.** Отступ 48px при подписи
   «08:00–09:20» шириной около 63px и отступе угла 7px — требовалось 70px.

2. **Фиксированная высота блока.** У `.lesson` стояло `height: 100%` —
   блок запирался по высоте ячейки, и содержимое выходило **за пределы
   самого блока**. Заменено на `min-height`.

3. **Горизонтальный запас оказался вредным.** Когда время отвели по вертикали
   (`padding-bottom` 22px), отступ справа у подписей стал не нужен — но он
   остался. Он сужал колонку, и длинные ФИО рвались посреди слова:
   «Кудзина/ва», «Петриченко/ко», «Тоштемир/ов». Убран совсем, а
   `overflow-wrap` заменён с `anywhere` (рвёт слово на любом символе) на
   `break-word` (только когда слово реально не влезает).

4. **Высота в процентах.** У блока стояло `min-height: 100%`. Процент у
   табличной ячейки считается от высоты, которая для таблицы «авто», и
   превращается в ноль — цвет предмета не доходил до низа ячейки, и под
   блоком оставалась белая полоса. Теперь у блока и ячейки одно и то же
   значение в пикселях:

   | Ступень | Ячейка и блок |
   |---|---|
   | база, 620px (телефон) | 54px |
   | база (ноутбук) | 108px |
   | 1800px | 132px |
   | 2400px | 158px |
   | 3200px | 188px |

Проверяют `test_time_is_pinned_to_the_corner` (нижний отступ блока),
`test_meta_has_no_horizontal_reserve`, `test_words_are_not_broken_mid_word`,
`test_lesson_fills_the_cell_height`, `test_lesson_height_is_not_a_percentage`
и `test_lesson_block_is_not_height_locked` в `schedule/test_appearance.py`.
Проверка `test_lesson_fills_the_cell_height` идёт по всем ступеням и требует,
чтобы блок и ячейка совпадали.

## Времена пар в админке

Справочник общий для всего расписания. В списке видно, сколько занятий на
каждой паре; время правится прямо в таблице (`list_editable`), несколько пар
можно поправить за один раз. Клик по номеру открывает карточку.

Раньше в `LessonTimeAdmin` стояло:

```python
def has_add_permission(self, request):
    return not LessonTime.objects.exists()
```

Задумывалось как защита от мусора, но ломало реальную работу: часы в вузе свои,
и если учебный план не совпадает с уже заведёнными парами, новую пару было не
завести — админка отвечала 403. Именно это не давало внести расписание из
файла, где первая пара в 9.00, а в системе пары начинаются с 8.00.

Ограничение снято. Удаление закрывать не потребовалось: у
`Lesson.lesson_time` стоит `on_delete=PROTECT`, и пару, на которую ссылаются
занятия, удалить нельзя — защита на уровне базы, с понятным сообщением.

Проверяет `schedule/test_lesson_time_admin.py` (14 тестов): добавление при
непустом списке, правка в списке, запрет удаления занятой пары, права
сотрудницы без права на добавление.

## Раскладка блока занятия

```html
<div class="lesson">
  <span class="flag">замена</span>   <!-- только при замене, вне потока -->
  <div class="lesson-body">
    <div class="lesson-subject">Предмет</div>
    <div class="lesson-meta">преподаватель, аудитория</div>
  </div>
  <div class="lesson-time">06:00–08:00</div>   <!-- тоже вне потока, в углу -->
</div>
```

```css
table.sheet-table .lesson {
  display: flex;
  flex-direction: column;
  align-items: center;       /* по горизонтали — иначе flex растянет содержимое */
  justify-content: center;  /* по вертикали — предмет на одном уровне в ряду */
  padding: 22px 8px 16px;   /* сверху резерв под плашку, снизу под время */
  min-height: 112px;
  position: relative;       /* база для обеих абсолютных плашек */
}

.flag {
  position: absolute;       /* выведена из потока */
  top: 6px;
  left: 50%;
  transform: translateX(-50%);
  max-width: calc(100% - 16px);
  font-weight: 700;
}

.lesson-body {
  padding-bottom: 4px;      /* зазор до времени */
  width: 100%;
  max-width: 100%;
}
```

**Отступы считаются, а не подбираются.** Раньше сверху стояло 26px «с запасом»
и в широких ступенях 28px. Плашке нужно 22px: `top: 6` + кегль 10px в строку
1.2 + поля 1px×2 + рамка. Лишние 4–6px висели пустым местом над предметом.
Снизу стояло 22px против нужных 14px (`9.5 × 1.2` высота строки + `bottom: 3`),
и при переносе ФИО на две строки время ложилось на аудиторию.

Сейчас сверху 22px во **всех** ширинах, включая карточки. Это обязательно:
плашка не меняет кегль от ширины окна, поэтому и резерв под неё обязан быть
один. Если растить верхний отпуск вместе с шириной, предмет начнёт прыгать по
вертикали при изменении размера окна.

**Почему 112px.** Это худший случай, а не средний: предмет, ФИО на две строки
и аудитория — четыре строки. `4 × 12px × 1.45` = 70px, плюс 4px под ними,
плюс 22px резерва сверху и 16px снизу = 112px. Если `min-height` меньше,
одна ячейка с длинным ФИО растянет весь ряд, и соседние строки окажутся
разной высоты. У ячейки `td.slot` стоит та же высота: блок ниже ячейки —
под цветом предмета остаётся белая полоса, блок выше — ряд расползается.

Телефон сюда не входит: там кегль 10.5px и сетка 54px, длинное ФИО занимает
столько, сколько нужно, и ячейка растёт сама. Заставлять все строки телефона
быть высокими ради одного длинного ФИО значит уменьшить вдвое то, что чаще
всего открывают на телефоне.

**Почему плашка абсолютная.** Пока она была элементом flex-колонки, случалось
две вещи: занимала всю ширину ячейки красной полосой (элементы flex
растягиваются по поперечной оси) и, главное, добавляла свою высоту. Сумма не
влезала — и **предмет в ячейке с заменой стоял ниже, чем в соседних**.

**Почему резерв сверху на блоке, а не на обёртке.** Плашка лежит поверх и
высоты не добавляет, поэтому место под неё держит `padding-top` самого блока —
он одинаков для всех ячеек. Раньше резерв стоял в `.lesson-body` (внутри
группы, которую прижимало `margin-top: auto`), из-за чего без замены предмет
прилипал к верху, а с заменой уезжал вниз.

`margin-top: auto` и `padding-top` в обёртке больше не используются: их роль
перешла к `justify-content` и `padding` блока. **Возвращать нельзя:**
`margin-top: auto` молча отключает `justify-content` — центрирование перестаёт
работать, и симптом возвращается как «предмет стоит ниже соседних».

Проверяют:

- `schedule/test_lesson_spacing.py` — арифметика отступов: резерв сверху
  равен высоте плашки, снизу хватает на время, `min-height` покрывает четыре
  строки, ячейка и блок одной высоты, запас у карточки и таблицы общий
- `schedule/test_appearance.py` — `test_lesson_centres_its_children`,
  `test_badge_is_out_of_flow`, `test_badge_space_is_reserved_on_the_block`,
  `test_body_has_no_vertical_hacks`, `test_body_does_not_touch_the_time`
- `schedule/test_wide.py` — `test_badge_reserve_is_the_same_everywhere`:
  резерв одинаков на всех ширинах; `test_lesson_padding_grows` требует
  расти только боковым отступам, а не вертикальным

## Одинаковые названия в разном написании

SQLite сравнивает строки посимвольно, поэтому «ЭК-01» и «эк-01» для него — разные
значения. Раньше поиск справочника шёл точным `filter(name=...)`, и каждый
«немного другой» вариант написания в Excel создавал новый объект: в меню
появлялись две одинаковые группы, один предмет получал два цвета, а фильтр
по преподавателю отдавал только часть его занятий.

Сейчас сравнение идёт по нормализованному ключу — `schedule/normkeys.py`:
регистр убран, `ё` приводится к `е`, лишние пробелы схлопываются. Ключ хранится
в базе отдельным полем `norm_*`, которое пересчитывается при каждом `save()`, и
на него стоит ограничение уникальности. Значит дубль не появится даже если
создать его руками в обход формы — получится понятная ошибка, а не
500.

| Справочник | Ключ уникальности |
|---|---|
| Группа | название + курс |
| Преподаватель | ФИО |
| Предмет | название |
| Аудитория | корпус + номер |
| Тип занятия | название |

Оба разбора ячеек, csv и xlsx, понимают аудиторию одинаково: «А - 201» сохраняется
как корпус «А» и номер «201». Раньше разбор ячеек сохранял её как `name='201/А'`,
а xlsx-как `name='201', building='А'` — одна аудитория давала две строки.

Проверяется `schedule/test_merge_duplicates.py`.

## Безопасность

Что закрыто и чем это проверяется:

| Что | Как | Тесты |
|---|---|---|
| Сырые занятия | разбор записей без группыватель получают 302 на логин | `test_access.py` |
| Выгрузка Excel | открыта всем, 30 запросов в минуту с IP, кэш 60 с | `test_access.py`, `test_export_protection.py` |
| Удаление через массовый выбор | фильтр сверху, «Выбрать все» | `test_access.py` |
| Телефон и почта преподавателя | в публичных страницах не выводятся, в списке берутся только 4 поля | `test_access.py` |
| Живой поиск `/list/` | срез `PICKER_LIMIT = 50`, 30 запросов в минуту с одного IP, дальше 429 | `test_throttle.py` |
| Форма «Связаться с нами» | 5 отправок в час с одного IP, лимит считается до проверки полей и captcha | `test_throttle.py` |
| Вход в админку | 30 попыток POST на `/admin/login/` в час с одного IP, `AdminLoginThrottleMiddleware` | `test_throttle.py` |
| Формулы в выгрузках | ячейки книги принудительно текстовые, апостроф в CSV | `test_export_protection.py` |

Что осталось открытым намеренно: расписание группы, пары, преподавателя и
аудитории, а также выгрузка CSV — это публичные страницы, иначе расписание
не откроется анонимно.

Что стоит настроить на сервере:

- `DJANGO_DEBUG=0`, `DJANGO_ALLOWED_HOSTS=example.uz`,
  `DJANGO_CSRF_TRUSTED_ORIGINS=https://example.uz` — тогда автоматически
  включаются HTTPS-редирект, Secure-куки и HSTS
- `DJANGO_TRUST_XFF=1`, только если веб-сервер гарантированно переписывает
  `X-Forwarded-For`. Иначе за прокси у всех один IP и лимиты (`/list/`,
  форма контактов, вход в админку) считают всех вместе
- `DJANGO_TRUST_PROTO=1` — если сайт стоит за Apache, который терминирует TLS
  и пересылает запрос в приложение по http. Без этой настройки `SECURE_SSL_REDIRECT`
  (он включён при `DJANGO_DEBUG=0`) отвечает 301 на https, Apache пересылает
  запрос снова с тем же заголовком — и браузер залипает в цикле редиректов.
  Включать **только** вместе с директивой на стороне сервера, которая всегда
  перезаписывает заголовок, а не добавляет его:

  ```apache
  RequestHeader set X-Forwarded-Proto "https"
  ```

- Лимиты на уровне веб-сервера надёжнее кэша Django: последний по умолчанию
  локальный для процесса, при нескольких воркерах счётчики разъезжаются

## Бэкап и восстановление

### Почему нельзя просто скопировать файл

`db.sqlite3` меняется при каждой правке расписания. Обычный `cp` в этот
момент попадает на середину записи и получает копию, которая выглядит целой,
но не является: часть страниц записана, часть нет. Восстановление из неё
падает с `database disk image is malformed`, и данные уезжают на неделю
назад — до предыдущего бэкапа, который тоже был таким.

Поэтому копия снимается через `VACUUM INTO`: SQLite берёт блокировку на всё
время операции и пишет результат в новый файл целиком. Копия получается
согласованной, даже если в момент запуска кто-то правит расписание.

### Снять копию

```bash
# на сервере, где проект в /var/www/timetable
cd /var/www/timetable
bash tools/backup.sh
```

Копия попадает в `/var/backups/timetable/timetable_ГГГГММДД_ЧЧММСС.db`
с правами `600`. Скрипт после копирования прогоняет `PRAGMA integrity_check`
и удаляет копии старше 30 дней. Если копия не прошла проверку, старые не
трогаются, а скрипт завершается с ненулевым кодом.

Переопределить пути и срок хранения:

```bash
BACKUP_DIR=/home/den/bak KEEP_DAYS=7 bash tools/backup.sh
```

Если в системе нет `sqlite3` (минимальный образ, Alpine) — скрипт сам
возьмёт одноимённый модуль из Python в `.venv`, ничего ставить не нужно.

### Расписание по cron

```bash
crontab -e
```

```cron
# бэкап в 03:17 ночи. Минута не 00 — в полночь сразу лезут все задачи сервера
17 3 * * * cd /var/www/timetable && /bin/bash tools/backup.sh >> /var/log/timetable-backup.log 2>&1
```

Проверить, что задача отработала:

```bash
sudo -u deploy /bin/bash -c 'cd /var/www/timetable && bash tools/backup.sh'
tail -20 /var/log/timetable-backup.log
```

### Восстановление

Восстановление перезаписывает боевую базу, поэтому порядок строгий: сначала
снимаем копию текущего состояния — если восстановление окажется неудачным,
текущие данные будут потеряны безвозвратно.

```bash
sudo systemctl stop timetable          # или gunicorn, зависит от сервиса

# 1. страховка: сохранить то, что есть сейчас
cd /var/www/timetable
sudo -u deploy bash tools/backup.sh

# 2. подставить нужную копию
cp /var/backups/timetable/timetable_20261005_031700.db db.sqlite3
sudo chown deploy:deploy db.sqlite3
sudo chmod 600 db.sqlite3

# 3. убедиться, что файл читается и не битый
python3 -c "import sqlite3; print(sqlite3.connect('db.sqlite3').execute('PRAGMA integrity_check').fetchone()[0])"
python3 -c "import sqlite3; print(sqlite3.connect('db.sqlite3').execute('select count(*) from schedule_lesson').fetchone()[0])"

# 4. запустить обратно
sudo systemctl start timetable
```

Если `PRAGMA integrity_check` вернул не `ok`, восстановление не удалось —
откатывайте шаг 2 из копии, снятой на шаге 1, и разбирайтесь с копией.

### Сколько копий хранить

30 дней по умолчанию. Расписание меняется в начале учебного года, и именно
тогда нужно сравнивать «как было» с «как стало» — месяц истории это
покрывает, год хранить смысла нет: персональные данные преподавателей не
должны лежать без нужды.

## Health-check

`GET /healthz/` — для балансировщика, для systemctl и для человека.

```bash
curl -i http://127.0.0.1:8000/healthz/
```

```json
{"status": "ok", "db": true, "time": "2026-10-05T07:34:00+00:00"}
```

| Ответ | Когда |
|---|---|
| 200 | приложение отвечает, база читается |
| 503 | база недоступна, бита или без схемы |

Проверяется не «жив ли процесс», а реальная зависимость: сначала `SELECT 1`,
затем чтение одной строки из служебной таблицы `django_migrations`. Второй
запрос нужен потому, что SQLite создаёт файл при подключении — «файл
существует» ещё ничего не значит, нужна настоящая таблица.

Чего проверка не делает: она не пишет в базу, а значит не замечает состояние
«залочено на запись». Для SQLite это основной сбой при массовой правке. Обнаружить
его можно только попыткой записи, а health-check, который пишет, способен
заблокировать сайт сам.

Особенности, о которые легко споткнуться:

- **не уходит в редирект на https.** При `DJANGO_DEBUG=0` включён
  `SECURE_SSL_REDIRECT`, и без исключения проверка отдавала бы 301, а
  мониторинг решил бы, что всё упало. Исключение — `SECURE_REDIRECT_EXEMPT`
  в настройках
- **не требует логина и не подпадает под rate limit.** Иначе опрос с частотой
  раз в минуту получал бы 429
- **HEAD разрешён наравне с GET.** Часть систем мониторинга шлёт именно его, а
  405 они истолкуют как падение
- **не кэшируется:** `Cache-Control: no-store`
- **не раскрывает причину сбоя.** В ответе только признак; текст исключения и
  путь файла уходят в лог — иначе открытый эндпоинт стал бы источником сведений
  о структуре установки

Проверяется `schedule/test_health.py`.
## Ограничение развёртывания: одна реплика

Приложение рассчитано на **один хост и один воркер**. Это осознанное решение
для сайта одного вуза, а не недоработка:

- rate limit `/list/` считает запросы в `LocMemCache` — памяти процесса;
- база — SQLite, запись блокируется целиком.

При нескольких воркерах лимит умножается на их число, а
SQLite отвечает `database table is locked`. Если понадобится несколько
реплик или воркеров, нужен переезд на PostgreSQL и общий кэш (Redis или
Memcached) — см. задачу `05` в `audit_todos/`.

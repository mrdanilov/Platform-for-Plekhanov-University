## 🔴 Critical (Критические проблемы)

### 1. «Проверить файл» реально пишет в БД — grid-импорт игнорирует `dry_run`

- **Что:** `import_workbook(data, filename, dry_run=True)` вызывает `import_grid(data, filename)` — а у `import_grid` (`schedule/excel.py:344`) нет параметра `dry_run` вообще, и он пишет в БД под `transaction.atomic()`. Двухшаговость импорта работает только для плоского CSV-формата.
- **Где:** `schedule/excel.py:461-477` (`import_workbook`), `schedule/excel.py:344` (`import_grid`), вызов — `schedule/views.py:668`.
- **Почему критично** (подтверждено прогоном, реальный HTTP POST staff'а):
  ```text
  DB before upload: Lesson=0 Group=0 Subject=0 Teacher=0
  POST /import/ {'check':'1', file: grid.xlsx} -> 200
  UI: «Будет создано: 6 … Нажмите "Применить импорт", чтобы записать.»
  DB after "Проверить файл": Lesson=6 Group=5 Subject=6 Teacher=5 Room=1
  ImportLog rows:        0
  ```
  **Три последствия одновременно:**
  1. Пользователю показывают «проверка», а данные уже применены;
  2. `ImportLog` не пишется — у аудит-трейла нет следов изменения данных;
  3. В UI есть кнопка «Применить импорт», второй клик по ней запускает импорт повторно. Плюс на том же этапе срабатывает `_ensure_lesson_times`, создавая `LessonTime` без записи в лог.
- **Как чинить:** Добавить `dry_run` в `import_grid` и тот же `if dry_run: ... return` до `transaction.atomic()`; в `import_workbook` прокинуть флаг в оба вызова. Добавить регрессионный тест «после check-запроса число Lesson не меняется» — сейчас именно его отсутствие и скрыло баг.

### 2. Fallback в `import_workbook` применяет данные дважды и оставляет БД в промежуточном состоянии

- **Что:** `import_workbook` при `grid_result.errors` вызывает `import_schedule(...)` как «второй разбор». Но `import_grid` к этому моменту уже закоммитил свою транзакцию — «откатить и попробовать иначе» не выходит.
- **Где:** `schedule/excel.py:468-477`.
- **Почему критично:** Пользователь видит «Ошибки — файл не применён» (`import.html:96`), а в БД уже лежит часть записей от grid-разбора, плюс поверх может лечь flat-разбор. Данные расписания университета оказываются в смешанном состоянии из двух источников, и «исправить файл и загрузить заново» это не устранит (upsert не удаляет, см. находку 6).
- **Как чинить:** Оборачивать обе ветки в одну внешнюю `transaction.atomic()`; на ошибке grid — `transaction.set_rollback(True)` до fallback; в UI показывать, какая ветка сработала.

### 3. Open redirect: Referer используется как адрес возврата без валидации

- **Что:** `set_language` валидирует `next` (`startswith('/')` и не `//`), но при пустом `next` подставляет `request.META.get('HTTP_REFERER')` и повторно проверяет только `startswith('/')`. Значение `//evil.example` проходит и уходит в `Location`.
- **Где:** `schedule/views.py:316-322`.
- **Подтверждено:**
  ```http
  GET /lang/?lang=uz  c Referer: //evil.example        -> 302 Location='//evil.example'
  GET /lang/?lang=uz  c Referer: //evil.example/phish -> 302 Location='//evil.example/phish'
  GET /lang/?lang=uz  c Referer: https://evil.example  -> 302 Location='/' (ок)
  ```
- **Почему критично:** Пользовательский HTTP-заголовок попадает в `Location` без санитизации. Реальная эксплуатация через браузер ограничена (браузер шлёт абсолютный URL), поэтому вектор скорее «звёздочный», но это ровно тот класс дефекта, который эксплуатируется в связке с другими (отравление Referer через сторонний редирект, недоверенный прокси). Дёшево закрывается, эксплуатировать не надо.
- **Как чинить:** После fallback прогнать ту же проверку (`not startswith('//')` + `url_has_allowed_host_and_scheme()` из `django.utils.http`) — это канонический хелпер Django вместо самописных `startswith`.

## 🟠 High (Высокий приоритет)

### 5. SQLite + локальное файловое хранилище загрузок несовместимы с горизонтальным масштабированием

- **Что:** `DATABASES` — sqlite3 на файле `BASE_DIR/db.sqlite3` (`config/settings.py:119-124`); загруженные файлы — в `BASE_DIR/tmp_import` (`settings.py:168`); rate-limit — на `LocMemCache` (дефолт, `throttle.py:20`).
- **Где:** `config/settings.py:119-124, 168`; `schedule/throttle.py:6-16` (в коде честно описано, что при нескольких воркерах лимит перестаёт работать).
- **Почему серьёзно:**
  - **(а)** Rate-limit `/list/` при 2+ воркерах умножается на число воркеров — перебор букв для выкачивания списка преподавателей снова открывается;
  - **(б)** `tmp_import` на локальном FS — при нескольких репликах запрос «Применить импорт» после «Проверить файл» уйдёт на другую реплику, сессия хранит только имя файла (`views.py:640`), и импорт падает на «файл устарел, загрузите заново»;
  - **(в)** Подтверждённая локальная проблема даже в одном процессе: 4 параллельных импорта → `OperationalError: database table is locked` на всех потоках, 0 записей сохранено.
- **Как чинить:** Для одной реплики + runserver — ограничить импорт одним процессом (или advisory-lock на запись); при плане на несколько реплик/воркеров — PostgreSQL, `CACHES` на Redis/Memcached, и `tmp_import` заменить на временное хранилище с явным TTL либо хранить файл в сессии не по имени, а передавать содержимое в один POST.

- **Как чинить:** Либо (предпочтительно) добавить явный режим «полная замена» с предпросмотром списка удаляемых занятий и подтверждением, либо честно переписать документацию, указав семантику merge. Сейчас несоответствие кода и документации опаснее самого merge.

### 8. Продакшен-конфигурация неполна: за reverse-proxy сайт не отдаёт статику и уходит в редирект-цикл

- **Что:** Три конкретных блокера, все подтверждены прогоном при `DJANGO_DEBUG=0`:
  - `SECURE_PROXY_SSL_HEADER` не задан, при этом `SECURE_SSL_REDIRECT = not DEBUG` (`settings.py:53`). За nginx с TLS-терминацией: `GET /` c `X-Forwarded-Proto: https` → 301 на `https` → nginx снова → бесконечный цикл.
  - `STATIC_ROOT` не задан, `collectstatic` падает с `ImproperlyConfigured`, WhiteNoise нет. При `DEBUG=0` runserver не раздаёт статику → `GET /static/schedule/style.css` → 301, ноль байт. Сайт без CSS/JS.
  - `manage.py check --deploy` с настройками по умолчанию даёт 5 предупреждений (`security.W004/W008/W012/W016/W018`), т.е. дефолт безопасен лишь случайно: `ALLOWED_HOSTS=['localhost','127.0.0.1','[::1]']` превращает забытый `DJANGO_DEBUG=0` в 400 на любом реальном хосте (проверено) — но ценой является неработающий сайт и traceback в логах.
- **Где:** `config/settings.py:43-58, 185` (нет `STATIC_ROOT`), `README:306-315` (раздел «Что стоит настроить на сервере»).
- **Как чинить:** `SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')` (только при гарантированном переписывании nginx — того же условия, что уже документировано для XFF); `STATIC_ROOT = BASE_DIR / 'staticfiles'` + раздача nginx или WhiteNoise; добавить эти два пункта в README рядом с существующим списком.

### 9. Импорт создаёт дубли сущностей при различиях в регистре / «ё»

- **Что:** Внутри одного запуска ключ кэша нормализован (`_norm_key = lower() + ё→е`, `importer.py:117`), но запрос в БД идёт по точному значению: `model.objects.filter(**kwargs).first()` (`importer.py:153`), `model.objects.filter(**{field: lookup}).first()` (`excel.py:335`). Уникальных ограничений на `Teacher.full_name`, `Subject.name`, `Room`, `LessonType.name` нет вообще (в `db.sqlite3` — 0 индексов на `schedule_teacher`).
- **Где:** `schedule/importer.py:147-165`, `schedule/excel.py:329-341`; модели — `schedule/models.py:7-92`.
- **Подтверждено:** Два импорта CSV с `ЭК-01`/`Финансы` и `эк-01`/`финансы` дали:
  ```python
  Group: [(1, 'ЭК-01'), (2, 'эк-01')]
  Subject: [(1, 'Финансы'), (2, 'финансы')]
  ```
  Две группы одного курса и два предмета с разными `id`.
- **Почему серьёзно:** Расписание показывает дубли (две «ЭК-01» в меню, один и тот же предмет разными цветами), фильтр по группе/преподавателю делит занятия между двумя записями, `uniq_lesson_slot` перестаёт защищать (у разных `group_id` слот не конфликтует), объём базы растёт при каждом «немного другом» написании в Excel.
- **Как чинить:** Фильтровать по нормализованному ключу (`__iexact` + `replace('ё','е')` приводить к вычисляемому полю или к `Case/When`), добавить `UniqueConstraint` на нормализованное имя для `Subject` / `LessonType` / `Room.building+name` / `Teacher.full_name`, и мигрировать существующие дубли перед включением ограничения.

### 10. Гонка «прочитал — потом создал» в обоих импортёрах

- **Что:** Оба парсера делают `Lesson.objects.filter(...).first()` и при `None` — `Lesson.objects.create(...)`, без `get_or_create` / `update_or_create` и без `select_for_update`. Единственный барьер — partial unique `uniq_lesson_slot`, который при гонке даёт `IntegrityError`.
- **Где:** `schedule/importer.py:324-348`, `schedule/excel.py:418-432`.
- **Почему серьёзно:** Два сотрудника жмут «Применить импорт» одновременно (штатная ситуация в начале учебного года). Один получает невнятный 500 вместо сообщения «занято», и — важнее — из-за транзакции откатывается весь импорт этого сотрудника, включая уже корректно разобранные строки (см. находку 5 про `database table is locked`).
- **Как чинить:** `update_or_create` по ключу слота внутри `transaction.atomic()`, `IntegrityError` ловить и превращать в `result.errors` со строкой файла, а не в 500.

- `set_language` меняет cookie по GET-запросу — изменение состояния через GET (только cookie, поэтому некритично).
- `i18n.translate` делает `.format(**kwargs)` по словарям (`i18n.py:171`); любая будущая строка с `{}` без kwargs вызовет `KeyError` и 500. Стоит завершать на `str.format_map` с пустым dict или запретить скобки в словарях.
- `onclick="window.print()"` в `_block.html:30` — inline-обработчик, помешает строгому CSP.
- `captcha.py` использует `random`, а не `secrets` (`new_question`, `render`) — для визуального шума некритично, но переход на `random.SystemRandom` стоит ноль усилий.
- `export_csv_view` (`views.py:699`) публичен и отдаёт полный дамп расписания с ФИО всех преподавателей без rate limit — задокументировано как осознанное решение, но это готовый датасет для скрейпинга персональных данных.
- `tests.py` рядом с `test_*.py` в том же пакете — при `manage.py test schedule` подхватываются оба, имена разнородные (`test_ui.py`, `tests.py`); файл `tests.py` лучше переименовать.
- `seed_menu_demo.py` — management-команда, создающая демо-данные, лежит в репозитории и создана для «проверки меню»; в проде не опасна (идемпотентна), но стоит пометить как dev-only в `help`.
- `tools/make_logo.py` требует `Pillow`, которого нет в `requirements.txt` — ожидаемо (разовый инструмент разработчика), но стоит указать в README явно, что Pillow не входит в runtime-зависимости приложения.
- **Нет `.env.example`** — перечень обязательных переменных приходится собирать вручную из текста README.

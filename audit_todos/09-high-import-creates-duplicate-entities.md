# 09 · 🟠 Импорт создаёт дубли сущностей (регистр, «ё»)

**Severity:** High — расписание делится между двумя записями, защита слота перестаёт работать
**Статус:** ⬜ не начато · **Оценка:** ~2-3 часа (фикс + миграция + чистка дублей)
**Зависит от:** `01` · **Блокирует:** `06`

## Где

- `schedule/importer.py:117` — `_norm_key(value) = _norm(value).lower().replace('ё','е')`
- `schedule/importer.py:147-165` — `ensure()`: кэш по нормализованному ключу, но
  запрос в БД идёт по **точному** значению: `model.objects.filter(**kwargs).first()`
- `schedule/excel.py:329-341` — `_get_or_create()`: то же, `filter(**{field: lookup})`
- Модели без ограничений: `schedule/models.py:7` (`Teacher`), `:45` (`Subject`),
  `:66` (`Room`), `:82` (`LessonType`) — уникальных индексов нет вообще
  (в `db.sqlite3` на `schedule_teacher` — 0 индексов)

## Что не так

Внутри одного запуска кэш нормализован, поэтому дубли внутри файла не появляются.
Но **между** запусками каждый раз делается точный `filter(name='...')` — и SQLite
сравнивает строки с учётом регистра. `ЭК-01` и `эк-01` — разные строки, значит
создаются два объекта.

## Доказательство

```
import CSV: Группа=ЭК-01, Предмет=Финансы
import CSV: Группа=эк-01, Предмет=финансы
-> Group:    [(1, 'ЭК-01'), (2, 'эк-01')]
-> Subject:  [(1, 'Финансы'), (2, 'финансы')]
```

Два одинаковых по смыслу предмета с разными `id`, потому импорт назначает им разные
цвета из палитры (`importer._pick_color`), и в расписаении они выглядят как разные предметы.

## Почему серьёзно

- Меню показывает «ЭК-01» дважды, один и тот же предмет — разными цветами.
- Фильтр по группе/преподавателю делит занятия между двумя записями — часть расписания
  «исчезает» из выдачи.
- `uniq_lesson_slot` (partial unique на `group_id, day, lesson_time_id, week_parity`)
  перестаёт защищать: у разных `group_id` слот не конфликтует.
- Объём БД растёт при каждом «немного другом» написании в Excel.

## Направление фикса

1. Фильтровать по **нормализованному** ключу: `__iexact` плюс приведение `ё`→`е`
   к вычисляемому полю (или `Case/When` в аннотации).
2. Добавить `UniqueConstraint` на нормализованное имя для `Subject`, `LessonType`,
   `Room.building+name`, `Teacher.full_name`.
3. **До** включения ограничений — миграция данных: найти существующие дубли, слить их
   (переназначить `Lesson.teacher`/`subject`/`room` на «канонический» объект и удалить
   дубль). Порядок важен: сначала чистка, потом constraint.
4. Продублировать ключ в денормализованное поле с `db_index=True` для скорости выборки.

## Критерии приёмки

- [ ] Повторный импорт `эк-01`/`финансы` после `ЭК-01`/`Финансы` не создаёт новых объектов.
- [ ] `manage.py migrate` на существующей БД проходит (дубли слиты).
- [ ] Попытка создать дубль через админку даёт понятную ошибку валидации, не 500.
- [ ] `python manage.py test schedule` проходит (часть тестов может потребовать обновления
      фикстур — проверить).
- [ ] Уникальные индексы видны в `PRAGMA index_list` для затронутых таблиц.

## Откат

Откат constraint-миграции возможен (`migrations.RunPython` в обратную сторону), но
**слитые дубли не восстановить** — откат данных возможен только из бэкапа (задача `19`).
Поэтому перед применением обязателен бэкап.

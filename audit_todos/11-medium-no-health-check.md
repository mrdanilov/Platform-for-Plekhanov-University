# 11 · 🟡 Нет health-check эндпоинта

**Severity:** Medium — балансировщик/оркестратор не может отличить «жив» от «падает на БД»
**Статус:** ⬜ не начато · **Оценка:** ~20 мин
**Зависит от:** ничего

## Где

`config/urls.py`, `schedule/urls.py` — маршрута `/healthz/` нет (проверено: ни `health`,
ни `readyz`, ни `ping`).

## Что не так

Приложение без health-check отвечает балансировщику одинаково в двух разных ситуациях:
«процесс жив и БД читается» и «процесс жив, но БД недоступна/залочена». Второй случай
сейчас вполне реален — SQLite целиком блокирует запись при импорте (см. `05`, `10`),
и сайт отдаёт 500, оставаясь «зелёным» для инфраструктуры.

## Направление фикса

1. Добавить `@require_GET`-вьюху `/healthz/` (на уровне `config/urls.py`, чтобы не тянуть
   зависимости приложения).
2. Проверять **реальную зависимость**, а не просто «процесс жив»: `SELECT 1` по БД
   (дешёвый, не трогает таблицы приложения).
3. Ответ: 200 + короткий JSON (`{"status":"ok","db":true}`); при ошибке БД — 503,
   чтобы оркестратор убрал под из балансировки.
4. Эндпоинт не должен попадать под rate limit и не требовать авторизации.

## Критерии приёмки

- [ ] `GET /healthz/` возвращает 200 и признак доступности БД.
- [ ] При недоступной БД возвращается 503 (проверить подменой `DATABASES` в тесте).
- [ ] Эндпоинт не тронут `throttle_ok` и не требует логина.
- [ ] В README описан маршрут и ожидаемый код ответа.

## Тест

```python
class HealthTests(TestCase):
    def test_ok(self): assertEqual(self.client.get('/healthz/').status_code, 200)
    # плюс вариант с подменой DATABASES на битую -> 503
```

## Проверка

```bash
python manage.py test schedule
curl -i http://127.0.0.1:8000/healthz/
```

## Откат

Удаление маршрута и вьюхи. Миграций нет.

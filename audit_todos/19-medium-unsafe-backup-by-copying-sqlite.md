# 19 · 🟡 Бэкап копированием живого `db.sqlite3`

**Severity:** Medium — бэкап может оказаться неконсистентным, отката не будет
**Статус:** ⬜ не начато · **Оценка:** ~20 мин
**Зависит от:** `04` (бэкап должен храниться вне рабочей папки)

## Где

`README.md:349`: «Резервная копия — копия `db.sqlite3`.»
Файл БД: `config/settings.py:119-124` → `BASE_DIR / 'db.sqlite3'` (245 КБ, в рабочей папке).

## Что не так

Копирование файла SQLite, пока идёт запись, даёт **неконсистентную копию**: страницы
журнала могут быть скопированы в разном состоянии. Импорт при этом пишет постоянно
(и, см. `01`/`02`, может писать в неожиданный момент). Такой бэкап не восстанавливается
и обнаруживается только при попытке отката — то есть в худший момент.

Дополнительно: копия лежит рядом с исходниками в рабочей папке, а `.gitignore` содержит
`db.sqlite3` — то есть копия, названная иначе, попадёт в git.

## Направление фикса

1. Бэкап через API SQLite, а не копированием файла:
   - `sqlite3 db.sqlite3 "VACUUM INTO 'backup_YYYYmmdd.db'"` — безопасно на живой базе;
   - либо `sqlite3.Connection.backup()` из Python.
2. Хранить бэкапы **вне** `BASE_DIR` (отдельный каталог/диск), и добавить его в `.gitignore`.
3. Автоматизировать (cron/Task Scheduler, раз в день перед началом учебного дня).
4. **Проверять** бэкап: `PRAGMA integrity_check` на копии. Непроверенный бэкап хуже
   отсутствующего — он создаёт ложное чувщение безопасности.
5. Документировать процедуру восстановления в README.

## Критерии приёмки

- [ ] Скрипт бэкапа не копирует файл напрямую.
- [ ] Бэкап проходит `PRAGMA integrity_check` = `ok`.
- [ ] Бэкап восстанавливается: подмена файла и `manage.py runserver` поднимают рабочее
      расписание.
- [ ] README описывает создание и проверку бэкапа и процедуру восстановления.
- [ ] Каталог бэкапов вне репозитория и в `.gitignore`.

## Проверка

```bash
sqlite3 db.sqlite3 "VACUUM INTO '/tmp/backup_test.db'"
sqlite3 /tmp/backup_test.db "PRAGMA integrity_check;"
```

## Откат

Бэкап — операция только на чтение, откатывать нечего. Проверить, что новый скрипт
не пишет в исходную БД.
